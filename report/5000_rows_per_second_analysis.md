# Evaluation of the 5,000 rows/s replay

The producer sustained **4,999.87 raw rows/s** and Kafka acknowledged the entire replay. **The captured stream results were numerically correct but incomplete and late.** The strongest performance evidence is the delay in observing actual results. Clock jumps made the saved Flink counters unreliable as measurements of processing capacity. ## Workload and correctness

The run used the selection documented in Test 2, with 190,000 rows skipped and 500,000 replayed per input file for November 8 and 9, 2021. Flink ran locally in WSL2 at parallelism 3 against eight Kafka input partitions, with a one-second event-time watermark allowance. The subscriptions were `INCAC.FR` and `INEUN.NL`. Producer preflight measured 841,632 eligible prices, 44,088 quote-only events, 114,280 housekeeping or metadata events, and zero rejected rows. All eligible prices used the capture date because the trading date was blank. The largest backward step in trade time was 512 ms, and preflight found zero additional watermark delay was needed to avoid crossing a window boundary for this particular selection. The implementation follows assignment §§3.1–3.3 for the evaluated cases. It uses exchange-qualified symbol keys and midnight-aligned five-minute market-time windows. Each nonempty window takes the latest eligible `Last` by trading time, breaking timestamp ties by source order. EMA38 and EMA100 start at zero and use the assignment's `2/(j+1)` weight. A BUY requires previous EMA38 ≤ EMA100 and current EMA38 > EMA100, with the inequalities reversed for a SELL. The first positive window can therefore produce a BUY from equal zero EMAs. The worker updates state for all eligible symbols and filters output by subscription. Empty windows leave the previous EMA in place, and missing trading dates use the capture date under the documented fallback. This slice gives limited coverage of late events, SELLs and scalability across exchanges. Of its eligible prices, 771,479 were FR, 66,604 NL and 3,549 ETR. Raw backlog is producer acknowledgements minus the Flink decode counter. Kafka lag is broker end offset minus the Flink source read offset, summed over partitions and including progress markers. Both Flink values come through the same REST metrics store. At the end of input the snapshot implies roughly **2,750 raw rows/s** over the 200 s ingest period, but metric freshness is unknown, so this is an apparent rate rather than a measured worker capacity. The 0 rows/s stretches and sudden jumps are unreliable as evidence of stops or bursts. The worker was still reported `RUNNING` at the last sample. The saved log ends before the default 90 s drain timeout and records no terminal failure. [Inspector metrics](../code/Pipeline/inspect_run.py#L169) · [Peak through first finished sample](../code/logs/trading-events-20261119-140727-977358684/worker.log#L75)

The producer and inspector logs both show roughly 199 s wall-clock jumps relative to monotonic elapsed time. I checked the installed Flink 1.20.0 JAR. `MetricFetcherImpl.update()` gates refreshes on `System.currentTimeMillis() - lastUpdateTime`. A forward jump followed by a backward correction can leave a cached offset, count and watermark in place. New EMA rows appeared while all three reported metrics were frozen. Even with this measurement problem, actual output observation fell behind. Both BUYs were observed at least about **16 s** after the producer acknowledged the first marker that made their window eligible. The November 9 07:40 `INEUN.NL` EMA was observed **at least about 150 s** after its eligible marker. Those lower bounds use producer monotonic time and the inspector's progress sequence. They measure time to observation and include sink and polling delay. ## Acceptable lag at 5,000 rows/s

The assignment calls for prompt advisories when the crossover is available and the rubric rewards low, stable latency. It gives no numerical Kafka backlog or latency limit. For this benchmark I propose **p95 ≤ 2 s and p99 ≤ 5 s** from the producer's first qualifying progress marker to observing the Kafka result. At 5,000 raw rows/s, 10,000 and 25,000 queued raw rows represent roughly two and five seconds of input. Use these as operational indicators alongside the oldest pending marker age and the slowest partition, since aggregate backlog does not guarantee result latency. The five-minute window and one-second event-time allowance govern correctness and are distinct from measured wall-time processing delay. [Assignment PDF, §3](../assignment/CS_E4780_Course_Project_2026.pdf#page=2) · [Evaluation rubric](../assignment/Evaluation_Criteria_26.md#system-implementation-12-points)

A short burst is acceptable if the backlog returns to baseline while input continues and the latency target holds. With continuing input at rate `λ` and sustainable worker capacity `μ > λ`, a backlog of `L` takes about `L/(μ−λ)` seconds to clear. After input stops it takes about `L/μ`. At 6,000 rows/s of capacity, 450,000 rows would need about 450 s to clear with input still at 5,000 rows/s, or 75 s after the producer stops. That backlog can be evaluated for a batch replay with an explicitly agreed drain deadline and an exact reference match. It exceeds the proposed live latency budget by a wide margin.

## Path to sustaining 5,000 rows/s

1. Repeat the baseline with a stable clock and fresh topics. Record monotonic result observation against the producer's marker journal, then capture per-subtask busy, backpressured and idle time, source offsets and window watermarks. Record JVM and Python CPU and RSS, GC, swap, disk and Kafka fetch latency alongside those metrics. This distinguishes worker saturation from stale reporting and host resource pressure. [Flink backpressure metrics](https://nightlies.apache.org/flink/flink-docs-release-1.20/docs/ops/monitoring/back_pressure/) · [Kafka source metrics](https://nightlies.apache.org/flink/flink-docs-release-1.20/docs/connectors/datastream/kafka/#monitoring)
2. Benchmark the same selection at parallelism 3 and 4, then test 6 if keyed subtasks are saturated and there is CPU headroom. Parallelism 4 gives two Kafka partitions per reader. Keep the watermark and subscription settings fixed. For the first bundle experiment, compare the current 100 ms with 250 ms at the same bundle size, then test a larger bundle size if the record cap is reached. Measure tail latency as well as speed. [Worker flags](../code/Pipeline/streamworker.py#L246) · [Flink Python configuration](https://nightlies.apache.org/flink/flink-docs-release-1.20/docs/dev/python/python_config/)
3. If the limit remains, benchmark Kafka read throughput with a JVM source that only counts inputs, then add decode/classify and the keyed stage in turn. If the keyed stage is the limit, port that stage to a JVM Flink operator to remove Python/JVM state calls and serialization on its hot path. If classification dominates, try a typed input or JVM decoder while retaining full input accounting. Preserve close ordering, the subscription filter after state updates, marker barriers and the matching EMA and advisory rules. [Current pipeline](../code/Pipeline/streamworker.py#L223)
4. Accept the 5,000 rows/s configuration only when backlog is bounded under continuous replay, result latency meets the declared target, all eight terminal markers are processed, and the reference checker reports zero mismatches. Run a separate higher-rate test around 6,000 rows/s to establish headroom. Include the fixture for SELL correctness and a longer workload covering all three exchanges for the assignment's scalability claims.
